## 1. PRIMARY KEY
InnoDB는 테이블 데이터를 PK 순서로 정렬된 B+Tree에 저장한다. 이를 클러스터드 인덱스라고 한다. 단순한 식별자가 아니라 **행이 디스크의 어디에 놓일지**를 정한다.

```
PK 트리 (16KB 페이지 단위)
[1, 2, 3, 4] → [5, 6, 7, 8] → ...   ← 각 페이지에 행 데이터 전체가 들어 있음
```

### 안 만들면?
InnoDB가 알아서 생성한다.
- NOT NULL인 첫 UNIQUE 인덱스를 PK처럼 쓴다.
- 없다면 사용자에게 보이지 않는 6바이트 행ID를 생성한다.
  
통제할 수 없는 키가 생기기 때문에 PK는 항상 명시하는게 좋겠다.

### 왜 AUTO_INCREMENT가 유리할까?
상식적인 이유같다. 새 행을 항상 트리의 맨 끝 페이지에 붙일 수 있다. UUID처럼 무작위 값을 쓰면 새 행이 트리 중간에 끼어들어야 하고, 꽉 찬 페이지를 반으로 쪼개는 페이지 분할이 자주 일어나 쓰기가 느려지고 공간이 낭비될 수 있다.

#### AUTO_INCREMENT의 함정: 번호에 구멍이 생기는 경우
트랜잭션이 롤백되어도 이미 발급한 번호는 되돌리지 않는다. 그래서 1,2,3,5 처럼 **번호가 비는 현상은 정상**이다. "ID가 연속이니 마지막 ID = 총 캐릭터 수"라고 가정하는 코드는 버그를 야기한다.

#### AUTO_INCREMENT의 함정: 서버를 여러 대로 나누면?
DB가 여러 대가 되면 각 DB의 AUTO_INCREMENT가 서로 같은 번호를 낸다. 그래서 대규모 서비스라면 `서버 번호+시간+순번`을 비트로 조합한 64비트 식별자를 생성하기도 한다.

### 복합PK
PK는 컬럼 여러 개를 묶어 만들 수 있다. 예를 들어 인벤토리를 `PRIMARY KEY (character_id, slot)`으로 설계하면 별도 inventory_id 없이도 행이 식별되고, 한 캐릭터의 아이템이 디스크상 붙어 저장되어 "이 캐릭터 인벤토리 전부 읽기"가 빨라진다.



### 예상 질문
- PK로 UUID를 쓰면 문제가 될까? → 무작위 삽입으로 인한 페이지 분할, 16바이트라 다른 인덱스까지 커짐
- PK가 없는 테이블은 어떻게 될까?

## 2. 자연키, 대리키

| | 자연키 (login_id, 캐릭터 이름) | 대리키 (AUTO_INCREMENT 번호)|
|---|---|---|
|의미|있음|없음|
|변경 가능성|있음 (이름 변경권)|	없음|
|크기	|큼, 가변 길이 | 작음, 고정 8바이트
|단점	|바뀌면 참조하는 모든 곳을 수정|중복 방지용 UNIQUE를 따로 걸어야 함

비즈니스 영역에서 이미 의미를 가지면 자연 키, 임의로 번호를 부여하는 경우는 대리 키 이다.
>> 상식적으로 대리키가 유리해보인다;;

### 키의 크기가 중요한가?
InnoDB의 다른 모든 인덱스는 행 위치 대신 PK값을 들고 있다. PK가 32바이트 문자열이면 이름 인덱스, 레벨 인덱스 등 모든 인덱스에 32바이트가 반복해서 붙는다.

## 3. UNIQUE

내부적으로는 **인덱스**이다.
UNIQUE를 걸면 그 컬럼으로 정렬된 인덱스가 만들어지고, 삽입할 때 인덱스에서 같은 값이 있는지 찾아 중복을 막는다. 즉, **삽입마다 인덱스 갱신 비용이 든다.**

### 서버 코드만으로는 중복을 확인하기에 부족하다.
캐릭터 이름 중복 검사를 서버에서 이렇게 했다고 가정하면
```
1. SELECT로 닉네임 '검사'가 있는지 확인
2. 없으면 INSERT
```
두 유저가 동시에 '검사'로 캐릭터를 만들면, 두 워커 스레드가 모두 1번에서 "없음"을 보고 둘 다 INSERT할 것이다. 전형적인 타이밍 문제이다.

UNIQUE 제약을 사용하면 DB가 둘 중 하나를 `ERROR 1062 Duplicate entry`로 거부한다. 그래서 정석은 **검사는 UNIQUE에 맡기고, 서버는 1062 에러를 받아 응답하는 것**이라고 한다.

### NULL과 UNIQUE
MySQL에서 NULL은 "알 수 없는 값"이라 서로 같다고 보지 않는다. 그래서 UNIQUE 컬럼에 NULL은 여러 개 들어갈 수 있다. PK가 NOT NULL을 강제하는 이유이기도 하다.

### 복합 UNIQUE
`UNIQUE (character_id, slot)`은 두 값의 조합이 유일하다는 뜻이다. (1, 0)과 (2, 0)은 공존할 수 있지만 (1, 0)은 두 번 들어갈 수 없다.

## 4. FOREIGN KEY

### 하는일
자식 테이블의 값이 부모 테이블에 실제로 있는지 DB가 검사한다.
- 자식 INSERT/UPDATE 시: 부모가 있는지 확인 (락 걸겠다)
- 부모 DELETE 시: 자식이 남아 있으면 어떻게 할지 결정

### 부모를 지울 때의 옵션
|옵션|	동작|
|---|---|
|RESTRICT / NO ACTION (기본값)|	자식이 있으면 삭제 거부|
|CASCADE	|자식도 함께 삭제|
|SET NULL	|자식의 FK 컬럼을 NULL로|

`CASCADE`는 편리해 보이지만 **계정 하나를 지웠더니 캐릭터, 인벤토리, 우편까지 연쇄 삭제**되는 사고로 이어질 수 있다.

### 숨은 비용
- FK 컬럼에 인덱스가 없으면 InnoDB가 자동으로 만든다.
- 자식 행을 삽입할 때 부모 행에 **공유 락**을 잡는다. 동시 접속이 많을 때 락 대기나 데드락의 원인이 될 수 있다.
- DB를 여러 대로 나누면, 다른 DB에 있는 부모는 검사할 수 없다.

#### 안쓰기도 한다.
FK를 빼고 서버 로직으로 무결성을 보장하는 곳이 꽤 있다고 한다. 또한 캐릭터 삭제는 실제로 지우지 않고 `is_deleted = 1` 처럼 표시하는 **소프트 삭제**를 쓰기도 한다고 한다. 이는 복구 요청(실수로 삭제), 운영 조사, 로그 추적 때문이다.

### 예상 질문
- FK를 쓰나요? → "무결성을 DB가 보장해 주는 장점이 있지만, 검사 비용과 락, 샤딩 제약 때문에 트래픽이 큰 DB에서는 서버 로직으로 대체하기도 한다"
- 캐릭터를 삭제하면 DB에서 바로 지우나요?

## 5. NOT NUL, DEFAULT, CHECK
### NULL은 왜 피하나: 3값 논리
SQL의 비교 결과는 참, 거짓, 그리고 **알 수 없음(UNKNOWN)** 세 가지이다. NULL과 무엇을 비교하든 결과는 UNKOWN이고, WHERE은 참인 행만 통과시킨다.
```
WHERE gold = NULL      -- 항상 아무것도 안 나옴 (UNKNOWN)
WHERE gold IS NULL     -- 이렇게 써야 함
WHERE gold <> 100      -- gold가 NULL인 행은 결과에서 빠짐!
```
마지막 줄 처럼 "100이 아닌 캐릭터"를 찾았는데 NULL인 캐릭터가 조용히 빠질 수 있다. 그래서 의미상 반드시 값이 있는 컬럼은 `NOT NULL DEFAULT 0`처럼 기본값을 주는게 원칙이다.

### DEFAULT
INSERT에서 생략한 컬럼에 들어갈 값이다. 스키마가 바뀌어 컬럼을 추가할 때도, 기존 서버 코드의 INSERT문을 고치지 않아도 되겠다.

### CHECK
값의 범위나 조건을 DB가 강제한다. 위반하면 `ERROR 3819`가 난다. 

WHERE과 다른 점은 WHERE은 정상 분기문, CHECK는 ASSERT에 가깝다는 것이다.
>> MySQL은 8.0.16 전까지 CHECK를 문법만 받고 무시했어서, 오래된 스키마와 습관이 그대로 남아 있는 곳이 있기 때문에 덜 쓰는 편이라고 한다.

>> 저장 프로시저나 서버 코드에서 검증하는 문화가 강해, DB 제약은 PK·UNIQUE 정도로 최소화하는 경우가 많다고 한다.

#### 제약은 마지막 방어선이다. (assert)
골드를 차감할 때 CHECK에 걸려 에러가 나는 건 버그가 DB까지 도달했다는 뜻이다. 하지만 골드가 부족한 경우는 버그가 아니라 분기로 처리해야 한다. 때문에 보통 골드 차감 로직은 이렇게 쓴다.
```
UPDATE characters SET gold = gold - 5000
WHERE character_id = 2 AND gold >= 5000;
```
그리고 **영향받은 행 수가 0이면 골드 부족**으로 처리한다. 확인과 차감이 한 문장 안에서 원자적으로 일어나 레이스 문제도 없다.

## 6. 자료형

### 정수
|타입	|크기|	범위 (SIGNED)|	쓰임|
|---|---|---|---|
|TINYINT	|1B	-128 ~ 127|	플래그(0/1), 작은 상태값|
|SMALLINT	|2B	약 ±3.2만|	슬롯 번호|
|INT	4B	|약 ±21억	|레벨, 아이템 템플릿 ID|
|BIGINT	8B	|약 ±922경	|캐릭터 ID, 재화|

UNSIGNED 컬럼끼리 빼서 음수가 나오면 에러가 나니, 계산이 오가는 재화는 SIGNED|`CHECK (gold>=0)`로 두는 경우도 많다고 한다.

### 문자열
- `VARCHAR(16)`의 16은 바이트가 아니라 글자 수이다. utf8mb4에서 한글은 한 글자에 3바이트, 이모지는 4바이트이다.
- `CHAR(n)`은 고정 길이로 남는 공간을 공백으로 채운다. 국가 코드처럼 길이가 항상 같은 값에 쓴다.
- MySQL의 `utf8`은 3바이트까지만 지원해 이모지를 담지 못한다. 때문에 필요하다면 `utf8mb4`를 사용해야한다.

### 날짜

||DATETIME	|TIMESTAMP|
|---|---|---|
|범위	|1000 ~ 9999년|	1970 ~ 2038년|
|시간대|	저장한 값 그대로	|UTC로 저장, 조회 시 세션 시간대로 변환|

TIMESTAMP의 2038년 문제는 32비트 정수로 초를 세기 때문에 글로벌 서비스라면 시간대 처리를 어떻게 할지 팀 규칙이 중요하다. (예: DB에는 모두 UTC로 저장)

### 실수
`FLOAT`, `DOUBLE`은 여기에서도 근삿값이라 0.1+0.2 == 0.3이 아니다. 

**현금 결제 금액은 `DECIMAL`**을 쓴다. 

게임 재화는 소수점이 없으니 정수로 충분하다.

#### 최대한 작게 잡는 편이 좋다.
행이 작을수록 16KB 페이지 하나에 더 많은 행이 들어간다. 같은 쿼리에 읽는 페이지 수가 주록, 메모리 캐시(버퍼 풀)에도 더 많이 올라간다. 단, 재화처럼 **커질 가능성이 있는 값은 아끼지 말고 BIGINT**를 쓰는게 낫겠다. 나중에 타입을 바꾸려면 큰 테이블 전체를 다시 써야 해서 라이브 서비스에서는 아주 부담스럽겠다.
